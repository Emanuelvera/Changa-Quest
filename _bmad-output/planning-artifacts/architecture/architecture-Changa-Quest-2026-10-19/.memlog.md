- (decision) Adoptar una aplicación REST monolítica modular con paradigma N-Layers según Guia-API-Rest-N-Layers.pdf. Presentation depende de BusinessLogic, BusinessLogic depende de DataAccess y Entities, DataAccess depende de Entities; API depende de Presentation. Core es soporte compartido, no una quinta capa. Regla: impedir que proyectos dependan de capas superiores o que DataAccess dependa de BusinessLogic.
- (decision) Adoptar SDD orientado a TDD: el requisito y sus criterios de aceptación documentados son la fuente de intención; las pruebas se derivan de esa especificación antes de implementar. Ciclo obligatorio Red-Green-Refactor; el código implementa y no redefine unilateralmente el comportamiento.
- (decision) BusinessLogic es el único dueño de las reglas y transiciones de negocio; Managers coordinan casos de uso. Presentation traduce HTTP/DTOs, DataAccess implementa persistencia y Stores con EF Core, Entities contiene modelos compartidos sin referencia a capas superiores. Ningún controlador ejecuta reglas de negocio ni accede directamente al DbContext.
- (decision) La asignación de una changa debe ser atómica y persistir un máximo de una asignación activa por changa. La integridad debe protegerse en persistencia, y pruebas de integración deben cubrir intentos concurrentes contra el proveedor de base de datos seleccionado.
- (decision) La dirección exacta no se devuelve en listados ni detalles públicos; solo una consulta de tarea autorizada para la persona asignada puede incluirla. Las pruebas de aceptación cubren acceso antes y después de la asignación.
- (version) Versiones verificadas al 2026-10-19 con Microsoft Learn: .NET 10 LTS (10.0.13 como último parche publicado); ASP.NET Core 10 pertenece a esa línea; EF Core 10.0 es LTS y requiere .NET 10. Se adopta la línea principal 10; el parche exacto de EF Core y los paquetes se fijan al iniciar el repositorio y se mantienen alineados.
- (question) Proveedor y motor relacional para el demo y lanzamiento, entorno de despliegue, autenticación/autoridad de identidad, framework de pruebas, versiones exactas de paquetes y pipeline CI quedan diferidos hasta confirmar restricciones del curso y alcance operativo. No inferir que el demo puede operar con tareas reales.
- (constraint) La demo académica es local, usa datos ficticios y puede omitir reportes, bloqueos y revisión administrativa; el producto real requiere resolver legalidad, confianza, moderación y operación antes de habilitar tareas reales.
- (decision) Precisar ownership: un ChangaManager es autoridad única de escritura para el ciclo de vida de la changa y asignación, incluidos comandos concurrentes de cancelación, finalización y decisión administrativa. Las pruebas de integración cubren transiciones incompatibles que compiten.
- (decision) La proyección pública/autorizada se decide en BusinessLogic. Se revalida asignación para dirección exacta y asignación más consentimiento explícito mutuo para teléfonos en cada consulta que expone datos sensibles.
- (decision) La API usa Problem Details con application/problem+json para errores HTTP, diferenciando errores de regla/validación y errores técnicos sin filtrar detalles internos.
- (version) Precisión de versión verificada por revisión de fuentes oficiales: .NET SDK 10.0.402; .NET runtime y ASP.NET Core 10.0.13; EF Core 10.0.13. Todas son versiones de la línea .NET 10 vigente al 2026-10-19.
- (assumption) La interfaz se implementará como cliente web responsive que consume la API REST; la tecnología de interfaz y su distribución quedan diferidas. Confirmar que el curso no fija una tecnología distinta antes de inicializar el repositorio.
- (event) Revisión independiente completada: se reforzaron ownership de ciclo de vida, concurrencia, privacidad, composición de dependencias, contrato de errores, frontera del cliente web y precisión de versiones.
- (event) spine finalized
- (decision) Para la demo local, usar el proveedor SQL Server con una instancia LocalDB/Express, sujeto a confirmar que el entorno de la cátedra lo admite. La guía Guia-API-Rest-N-Layers.pdf no especifica motor ni proveedor; mantener el proveedor del producto real abierto.
- (decision) Adoptar xUnit para pruebas de unidad y aceptación .NET de la demo, con dotnet test; el ciclo TDD SDD-RGR del spine gobierna la implementación. La documentación oficial de Microsoft usa xUnit y dotnet test; versionar paquetes al inicializar la solución.
- (decision) Elegir Blazor WebAssembly como cliente web responsive separado, consumiendo la API REST; mantener la frontera API REST del architecture spine y el desarrollo UI en C#/.NET. La documentación oficial de Microsoft confirma que Blazor es una tecnología vigente para UI web y la línea ASP.NET Core 10; concretar plantilla y modo de despliegue al inicializar.
- (version) La cátedra permite .NET 10; conservar .NET SDK/runtime 10 y EF Core 10 como stack aprobado para esta solución, además de la verificación previa de versiones vigentes al 2026-10-19.
- (version) Verificación al 2026-10-20: Microsoft.EntityFrameworkCore.SqlServer 10.0.13 está publicado por NuGet y es el proveedor oficial de EF Core para SQL Server; xunit.v3 4.0.2 es estable y soporta .NET 8+; Microsoft Learn documenta Blazor bajo ASP.NET Core 10. Fuentes: https://www.nuget.org/packages/Microsoft.EntityFrameworkCore.SqlServer/10.0.13, https://www.nuget.org/packages/xunit.v3/4.0.2, https://learn.microsoft.com/en-us/aspnet/core/blazor/?view=aspnetcore-10.0.
- (decision) Adoptar /api/v1 y un documento OpenAPI versionado como contrato canónico de requests, responses, DTOs, nulabilidad, enums y errores; pruebas de contrato verifican API y cliente Blazor, y cambios incompatibles requieren nueva versión. Evita divergencias de wire format entre unidades construidas en paralelo.
- (decision) Una repetición de la toma ya confirmada por la misma persona devuelve la asignación existente; otra persona recibe HTTP 409 con el código estable changa_already_assigned. Evita resultados ambiguos si se pierde la respuesta después del commit.
- (decision) En modalidad de selección, asignación, resultado de la postulación elegida y cierre de postulaciones no seleccionadas forman una transacción atómica coordinada por ChangaManager; notificaciones se emiten luego del commit y su mecanismo durable queda diferido. Evita estados persistidos parciales.
- (decision) Ampliar el alcance de AD-4 a FR-7..FR-15 para las transiciones incompatibles sobre una changa y mapear CAP-1..CAP-6 directamente a FR, AD y alcance de demo, distinguiendo las capacidades del producto objetivo.
- (version) Verificación tecnológica independiente al 2026-10-20: el paquete de pruebas es NuGet xunit.v3 4.0.2 (xUnit v3), compatible con .NET 8 o posterior y por tanto con .NET 10; se fija el ID del paquete en el Stack. LocalDB/Express y runner/host/CI se verifican al inicializar.
- (event) Reviewer gate de actualización cerrado: se incorporaron las decisiones API-cliente, atomicidad/idempotencia y trazabilidad CAP; lint_spine terminó con 0 hallazgos.
